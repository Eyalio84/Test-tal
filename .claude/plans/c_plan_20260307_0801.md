## Architectural Decisions (locked in this plan)

### Runtime Theme Switching via SiteContent
- `SiteContent` row with `id: "active_theme"` stores the live theme ID (e.g. "restaurant")
- Server components call `getActiveTheme()` helper: reads `SiteContent.live` where `id='active_theme'`, falls back to `NEXT_PUBLIC_THEME` env var, then "jewelry"
- All pages that need theme data use `getActiveTheme()` instead of importing `activeTheme` directly
- Theme switching saves to `SiteContent.live` directly (no draft/publish needed for theme — it's a structural change, always live)
- Client side: active theme ID passed to Zustand store via Providers; `useAriaLive` reads `THEMES[activeThemeId]` to build dynamic ARIA_FUNCTIONS

### ARIA_FUNCTIONS Dynamic Injection
- `useAriaLive.ts` imports `THEMES` from `lib/theme.ts` (edge-safe, no DB)
- `useAria().activeThemeId` (from Zustand) selects the current theme config
- ARIA_FUNCTIONS descriptions rebuilt using `theme.aria.products` and `theme.aria.categories`
- On theme switch: update Zustand `activeThemeId` → ARIA_FUNCTIONS regenerate on next WebSocket connect

### "Edit Mode on Running Website" — Assignment to Plans
- Plan #3 (this plan): NOT included. The existing `/admin/editor` already provides draft editing.
- Plan #6 (Visual Editor v1): Add inline edit overlay directly on the live site — clicking any section activates edit controls in-place, changes go through existing draft→publish flow from Plan #2.
- Plan #7 (Visual Editor v2): Aria voice control of the in-place editor.
